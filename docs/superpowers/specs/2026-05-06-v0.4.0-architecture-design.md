## 1. Background

v0.3.0 shipped on `main` 2026-05-05 (PR [#41](https://github.com/mtheuma/epson2paperless/pull/41)) covering: WF-3620 ESC/I support, FS F source autodetection (#28), promise-contract reconciliation between the two scanners (the `errorReason + failOnce + rejectOnce` pattern is now in place at `src/scanner.ts:132-148` and `src/scanner-legacy.ts:159-219`), the `auto + fingerprint` cert-pinning bypass fix, KISS/DRY/YAGNI sweep 1, and the `dev`-PR CI gate. v0.3.1 followed (PR [#45](https://github.com/mtheuma/epson2paperless/pull/45)) adding protocol-diagnose mode. `dev` is currently at `package.json` `0.3.1`.

The architectural rebuild deferred from v0.3.0 is now in scope. The consolidated review identifies four root drivers (re-derived against current `dev`):

- **D1 — Divergent scaffolding duplication.** Both scanners independently own socket lifecycle + recv pump + rolling timeout + page-flush + back-page index + EXIF + finalize. Verified divergence today: recv-buffer strategy (deferred-concat in `scanner.ts:155` vs per-event `Buffer.concat` in `scanner-legacy.ts:258`).
- **D2 — Tangled state encoding (legacy).** `scanner-legacy.ts` contains the smoking-gun `getState()` workaround at lines 216–219 _("Defeat TypeScript's control-flow narrowing")_. ADF-vs-flatbed lives both in the state enum (six ADF-only states) and in handler-body conditionals.
- **D3 — Mechanical sub-flow repetition.** `scanner.ts` has 32 states; `scanner-legacy.ts` has 42. Three near-identical "STAT-then-pure-read-then-FIN" sub-flows in ESC/I-2; five copies of "ESC e + param + double-ACK" in legacy.
- **D4 — Async-encode glue (legacy).** ~80 LOC of `encodingDeferred[]` + `deferredImageChunks[]` + `PAGE_ENCODING` state at `scanner-legacy.ts:174-180, 685-773`, all glue to bridge async sharp encoding with continuing inbound packets.

Issue #43 (ET-2750 compatibility, currently triaging) adds a forward-looking constraint: the most likely hypothesis is "ESC/I-2 commands over plain TCP" — same protocol script as ET-4950, different transport. Whatever Group A produces should let an ET-2750 land as a one-line factory swap, not a refactor.

## 3. Engine API

### 3.1. Transport interface

The engine consumes an already-connected bidirectional byte stream. Connection setup, TLS handshake, certificate pinning, and protocol-specific transport selection live entirely in the consumer's factory.

```ts
// src/scan-session.ts

export type SessionTransportFactory = () => Promise<SessionTransport>;

export interface SessionTransport {
  write(buf: Buffer): boolean | void;
  /** Polite close after normal completion. */
  end(): void;
  /** Fail-fast destroy for error paths. */
  destroy(err?: Error): void;

  on(event: "data", cb: (chunk: Buffer) => void): this;
  on(event: "error", cb: (err: Error) => void): this;
  on(event: "close", cb: (hadError?: boolean) => void): this;
}
```

Both Node `tls.TLSSocket` and `net.Socket` satisfy this interface structurally — the engine never reaches into either. Tests use a tiny fake transport (no real stream semantics required).

**Engine responsibility:** "Given an already-connected byte stream, run this graph."
**Factory responsibility:** "Connect however this protocol requires, then return a stream."

> **M2 finding (2026-05-07).** The original "no wrappers needed" line was overoptimistic. ESC/I-2 panel hygiene depends on application-level teardown timing — sending UNLOCK before half-close, swallowing benign post-FIN ECONNRESET / EPIPE, no-op'ing destroy after a graceful end so close_notify lands. None of that belongs in the generic engine; none of it belongs in the orchestration shell either. Each protocol that needs this gets its own **transport adapter** module (`src/esci2/transport.ts` exporting `withEsci2UnlockOnDestroy(socket: tls.TLSSocket): SessionTransport`). The factory wires raw socket → adapter → engine. Future ESC/I-2-over-plain-TCP gets a sibling factory in `scanner.ts` reusing the same adapter unchanged. ESC/I, when ported to the engine in M3, gets its own adapter (`src/esci/transport.ts`) — do not unify with ESC/I-2's, the close-timing rules differ.

The dispatcher (`src/protocol-probe.ts` + `src/startup.ts:dispatchScanSession`) keeps probe / auto-detection logic. The factory is small. ET-2750 lands as a third dispatcher case (ESC/I-2 graph + plain-TCP factory + same `withEsci2UnlockOnDestroy` adapter) without engine or graph changes.

### 3.2. Graph data structure

```ts
// src/scan-session.ts

export interface Graph<Ctx> {
  initial: string;
  states: Record<string, GraphState<Ctx>>;
  /** Default rolling-timeout per dispatch. Per-scanner default; ESC/I-2 30s, ESC/I 60s. */
  timeoutMs: number;
  /**
   * Optional per-packet-type abort handlers run BEFORE state-specific
   * dispatch. Used for protocol-level meta-events (e.g. ESC/I-2 type
   * 0x9000 async fatal/cancel events handled at `scanner.ts:345-349`).
   * Returns `Error` to fail the session; returns `null` to ignore the
   * packet (e.g. ESC/I-2 ScanStart/Stop info events that the current
   * scanner just logs and continues).
   */
  globalAbortHandlers?: Record<
    number,
    (ctx: Ctx, packet: { type: number; payload: Buffer }) => Error | null
  >;
  /**
   * Optional pre-dispatch filter for packets to discard. Used for
   * protocol-level "wait for body" patterns (e.g. ESC/I-2 empty 0xa000
   * envelopes — the body follows in a subsequent packet). Receives
   * the current state name so a filter can scope itself per state
   * (e.g. ESC/I-2 filters empty 0xa000 globally EXCEPT in
   * POSTSCAN_*_STAT_DRAIN, where the same shape is the actual
   * drain-complete reply). Returns `true` to discard.
   */
  globalIgnoreFilter?: (packet: { type: number; payload: Buffer }, currentState: string) => boolean;
}

export type GraphState<Ctx> =
  | { kind: "static"; on: Record<number, StaticTransition<Ctx>> }
  | { kind: "decision"; decide: DecisionFn<Ctx> };

/**
 * A single write operation. Either concrete Buffer (resolved at module
 * load) or a `(ctx) => Buffer` thunk resolved at dispatch time.
 */
export type SendSpec<Ctx> = Buffer | ((ctx: Ctx) => Buffer);

export interface StaticTransition<Ctx> {
  next: string;
  /**
   * Bytes to write to the transport when this transition fires.
   * Single-value form for single-write commands; array form for
   * back-to-back multi-write patterns where wire ordering matters
   * (e.g. legacy ESC e: the opcode and the parameter packet are sent
   * back-to-back in the same tick, then host waits for two ACKs —
   * delaying the parameter write until after the first ACK changes
   * wire order and breaks replay tests).
   *
   * Engine writes are sequential in array order via `transport.write()`;
   * thunks resolve against the current ctx at dispatch time.
   */
  send?: SendSpec<Ctx> | SendSpec<Ctx>[];
  /**
   * Optional payload validator. The graph's `on:` table is keyed by IS
   * packet *type*; for protocols that further validate a payload byte
   * (notably ESC/I: every passthru reply is a `0x2000` envelope whose
   * payload byte 0 carries the protocol-level ACK / NAK, e.g. `0x06` for
   * ACK), the transition specifies a validator. Engine semantics: packet
   * type matches → run `validate(payload)`; if it returns `true`, apply
   * transition; if `false`, fail the session with a state-tagged error.
   * Validation is mechanical, not semantic — it does not promote the
   * state to the decision-point allowlist (§3.4).
   *
   * (For the "wait for body — ignore this empty envelope" pattern, use
   * the graph's `globalIgnoreFilter` instead. Validate-failure is a
   * hard error; the filter is a discard.)
   */
  validate?: (payload: Buffer) => boolean;
  flushPage?: PageFlush;
}

export type DecisionFn<Ctx> = (
  ctx: Ctx,
  packet: { type: number; payload: Buffer },
) => TransitionResult;

/**
 * Decision-fn return shape. Generic over Ctx so decisions can return
 * the same `SendSpec<Ctx>` shapes static transitions accept — concrete
 * Buffer, `(ctx) => Buffer` thunk, or arrays of either. Engine's
 * `resolveSend` + `writeAll` handle all shapes uniformly. Unifying
 * the type here keeps decision call sites aligned with static-transition
 * call sites and lets helpers be agnostic about which kind of state
 * they're authored for.
 */
export type TransitionResult<Ctx> =
  | { next: string; send?: SendSpec<Ctx> | SendSpec<Ctx>[]; flushPage?: PageFlush }
  | { error: Error };

export interface PageFlush {
  /** Returns finished JPEG bytes. ESC/I wraps a sharp() call; ESC/I-2 wraps Promise.resolve(jpegBuf). */
  encode: () => Promise<Buffer>;
  side: "front" | "back";
}
```

The graph is **plain frozen data**. The engine walks it; nothing else.

### 3.3. Builder API (authoring-only)

The builder runs at module-load time. `build()` returns a frozen `Graph` data structure; the engine never sees the builder.

```ts
// src/scan-session.ts

export function createGraph<Ctx>(initial: string, timeoutMs: number): GraphBuilder<Ctx>;

export interface GraphBuilder<Ctx> {
  state(name: string, def: StaticTransitions | DecisionDef<Ctx>): this;
  build(): Graph<Ctx>;
}

export function decision<Ctx>(fn: DecisionFn<Ctx>): DecisionDef<Ctx>;
```

Authoring example (legacy):

```ts
// src/esci/graph.ts

const g = createGraph<EsciCtx>("WELCOME", 60_000);
g.state("WELCOME", { on: { 0xa000: { send: buildLockPacket(), next: "LOCKING" } } });
// ...
g.state(
  "STATUS_2",
  decision((ctx, packet) => {
    const result = ctx.forcedSource
      ? { ok: true as const, source: ctx.forcedSource }
      : legacyDetectSource(packet.payload[0], ctx.duplex);
    if (!result.ok)
      return {
        error: new Error(
          `Unrecognised FS F status 0x${result.byte.toString(16).padStart(2, "0")} ` +
            `— please file a compatibility issue with LOG_LEVEL=debug output. ` +
            `Workaround: set ESCI_FORCE_SOURCE.`,
        ),
      };
    ctx.source = result.source;
    return { next: result.source === "flatbed" ? "RESET_PAREN" : "ADF_PRESRC_CMD" };
  }),
);

// Helper takes a (ctx) => number thunk so the source byte resolves at
// dispatch time, after STATUS_2 has populated ctx.source.
escEThenAck(g, "RESET_SRC", (ctx) => SOURCE_BYTE[ctx.source], "STATUS_READY");
// ... 4 more escEThenAck calls
export const esciGraph = g.build();
```

Helper definition:

```ts
function escEThenAck<Ctx extends { source: Source }>(
  g: GraphBuilder<Ctx>,
  prefix: string,
  sourceByte: (ctx: Ctx) => number,
  next: string,
): void {
  g.state(`${prefix}_CMD`, {
    on: { 0x06: { send: (ctx) => paramBlock(sourceByte(ctx)), next: `${prefix}_PARAM` } },
  });
  g.state(`${prefix}_PARAM`, { on: { 0x06: { next } } });
}
```

**Helper convention:** every helper takes an explicit `prefix: string`. No auto-numbering. Generated state names (e.g. `${prefix}_CMD`, `${prefix}_PARAM`) read identically in debug logs to today's hand-written enum entries.

**One-off states stay plain.** Helpers earn their keep through visible repetition; an N=1 state goes inline.

### 3.4. Decision-point allowlist

Computed transitions are reserved for genuine semantic decision points. The allowlist (extension requires spec change, not implementation drift):

| Scanner        | Decision point                    | What it decides                                |
| -------------- | --------------------------------- | ---------------------------------------------- |
| ESC/I (legacy) | `STATUS_2`                        | FS F byte → flatbed / adf-simplex / adf-duplex |
| ESC/I          | `START_POLL` / `START_POLL_READY` | FS G chunkSize=0 → poll FS F → re-issue FS G   |
| ESC/I          | `IMG_RECEIVING` end-of-page       | last page vs next page vs ADF-empty            |
| ESC/I          | async fatal / cancel handler      | which error to surface                         |
| ESC/I-2        | `STAT` length=0 vs >0             | drain or skip drain                            |
| ESC/I-2        | `IMG_DATA` zero-length retry      | retry vs `MAX_ZERO_IMG_RETRIES` exceeded       |
| ESC/I-2        | async fatal / cancel handler      | which error to surface                         |

Anything not on this list either uses static transitions or a helper. Adding any new decision point during implementation requires updating this list, not silently introducing one.

### 3.5. flushPage barrier semantics

> **Spec wording:** `flushPage` is a graph-dispatch barrier. The engine continues socket ingestion while a flush is pending, but no further IS packets are dispatched to state transitions, no `send` bytes are written, and no `next` state is entered until the flush resolves. A rejected flush fails the scan session through the common engine failure path.

Engine flow when a transition returns `flushPage`:

1. **Stage** `next` and `send` if present. Do **not** yet write to the transport; do **not** yet enter the next state. The barrier intent is host-side back-pressure: we don't want to ask the printer for the next response until the host has durably persisted the page, otherwise we re-create the buffering problem this feature is meant to remove.
2. Set `paused = true`.
3. `await flushPage.encode()` — returns finished JPEG bytes.
4. If `side === "back"`, append `pageIndex` to the back-page index list (always — both JPG and PDF output need it).
5. **Action-gated EXIF.** If `side === "back"` AND `action === "jpg"`, inject `setJpegOrientation(jpeg, 3)` (from `src/exif.ts`) before writing. For `action === "pdf"`, JPEGs stay unmutated; pdf-lib's `/Rotate=180` in `composePdfFromJpegs` handles back-page rotation. (This matches the existing `scanner.ts:493` behaviour and silently fixes the unconditional EXIF injection at `scanner-legacy.ts:785`, which double-rotates legacy duplex back pages in PDF mode today.)
6. Write JPEG to the per-session temp file (`page_NN.jpg`).
7. Clear `paused`.
8. Apply staged `send` (write to transport) if present.
9. Enter staged `next` state.
10. Pump the recv accumulator — any IS packets that arrived during the flush get dispatched now.

While `paused === true`, `socket.on("data")` only appends to `recvChunks`. No transitions fire. No bytes go on the wire. No timeout fires (see §3.6).

**M1 limitation:** no flush watchdog. A hung `sharp().toBuffer()` will block the session indefinitely. Acceptable in practice for current scan workloads (≤500MB raw-RGB peak for a 3-page A4 duplex @ 300dpi). A flush-timeout watchdog is a different primitive from the transport-level rolling timeout — separate enough to defer cleanly. Documented; revisit if it bites.

### 3.6. Engine internals (locked)

- **Recv buffer.** Engine standardises on the `recvChunks: Buffer[]` + deferred `Buffer.concat` shape from current `scanner.ts:155`. Replaces the per-event `Buffer.concat` from current `scanner-legacy.ts:230`. Architecture-review-confirmed perf win for fragmented packet streams.
- **Rolling timeout.** Engine-owned. Armed when a state is entered; cleared when that state's transition fires. **Suspended (cleared) for the duration of a `flushPage` barrier**: a hung host-side encoder is a separate failure mode from a hung transport, so it should not fire the dispatch timeout. Re-armed when the next state is entered after the barrier completes (i.e. at step 9 of §3.5). A flush-timeout watchdog is a future feature, not in M1. Per-scanner default (`Graph.timeoutMs`): ESC/I-2 30s, ESC/I 60s.
- **Terminal state.** A transition that targets `next: "DONE"` is interpreted as terminal. **`"DONE"` is reserved**: `createGraph(...).state("DONE", ...)` throws at build time (the engine guards against shadowing). On entering `"DONE"` the engine calls `transport.end()` (polite close), waits for `socket.on("close")`, runs `finalizeSession`, and returns `{ ok: true, finalCtx }` (where `finalCtx` is the post-run mutable ctx — used by orchestration shells that need to forward detected state to test hooks like `onSourceDetected` in `runEsciScan`).
- **Idempotent settlement.** The engine's internal `settle(result)` is guarded by a `settled: boolean` flag and is safe to call multiple times. The transport `"close"` handler also checks the flag — necessary because `settle()` calls `transport.destroy()`, which emits `"close"` synchronously on fakes (and asynchronously on real sockets), so the close handler would otherwise re-enter `settle()`.
- **Settlement always destroys (PR 1, revised post-review).** Every `settle()` call — success or failure, including natural-DONE success — invokes `transport.destroy()` (idempotent, wrapped in try/catch). `enterState("DONE")` issues a polite `transport.end()` first to give the peer a chance to FIN cleanly; settlement's `destroy()` is the resource-cleanup safety net for peers that don't (TLS close_notify timing is unreliable; some printers never send FIN). Adapters that want to no-op a redundant destroy after a polite end() do so via their own clean-close state — `withEsci2UnlockOnDestroy`'s `politelyClosed` gate is the canonical example. That gate is the right place for protocol-aware nuance ("we already closed politely vs we're aborting mid-flow"); the engine treats destroy uniformly and trusts the adapter layer. (An earlier PR-1 design split `settle({ ok: true }, { skipDestroy: true })` for the success path. PR-51 review surfaced that this can leak one socket per successful scan in the daemon when the peer doesn't send FIN; the split was reverted.) The cleanupStates post-scan-save fallback (v0.3.0 §3.3) bypasses `settle()` for its ok-resolution — it `resolve(...)`s the promise directly inside its async IIFE — but only AFTER the prior abort `settle({ ok: false })` has destroyed the transport.
- **Listener-replay tolerance (PR 1).** The engine tolerates `data` events fired at any point — including synchronously inside the `transport.on("data", cb)` registration call, before `enterState(graph.initial)` runs. Three coordinated mechanisms enforce this: (1) `let dispatching = false` is hoisted above all listener registrations to avoid TDZ; (2) the pump's gate skips when `currentState === ""` so a synchronous-during-registration replay buffers in `recvChunks` rather than crashing on a `graph.states[""]` lookup; (3) `void tryDispatch()` is invoked immediately after `enterState(graph.initial)` to drain anything the gate held. `FakeSocketBase`'s `queueMicrotask` buffering becomes a convenience rather than a correctness requirement.
- **Barrier `settled` re-checks (PR 1).** Inside the `flushPage` barrier, the engine re-checks `settled` after each `await` (`encode`, dynamic `import("./exif.js")`, `createSessionTempDir`, `fs.promises.writeFile`) before any further side-effect (file write, ctx mutation, staged send, entering the staged next state). If the transport closed or errored mid-barrier, `settle({ ok: false })` has already run; the barrier exits cleanly without leaking writes or state advances. The barrier always exits with `paused = false` even on the catch path, for flag consistency on subsequent settled-gated re-entries.
- **`transport.end()` throw tolerance (PR 1).** `transport.end()` inside `enterState("DONE")` is wrapped in try/catch. Real sockets can throw on already-destroyed (e.g. peer RST during DONE entry); pre-fix the throw routed through `tryDispatch`'s catch into `settle({ ok: false })`, misclassifying a successful scan (all pages flushed, finalize would have succeeded) as a failure. Post-fix the throw is swallowed and `setImmediate(doFinalize)` proceeds normally.
- **Fail-fast on unmatched packets in static states.** When a static state's `on:` table has no entry for the incoming packet type, the engine fails the session with `Unexpected packet type 0xYYYY in state X`. Mirrors the existing scanners' `ensure(...)` pattern — protocol violations should surface immediately, not become eventual rolling-timeout firings with the wrong diagnostic. Decision states have explicit control over what they consider unexpected (the decision function returns `{ error }` or routes to a different state).
- **Zero-page rejection on DONE.** A graph that reaches `"DONE"` without any `flushPage` having fired settles as `{ ok: false; reason: Error("Scan completed with zero image chunks") }`. Mirrors the v0.3.0 §3.3 contract for the post-scan-save fallback's complement (zero-image completion is a real failure mode, not a silent success). Test-only escape: `RunScanSessionOpts.allowZeroPages?: boolean` for unit tests that exercise scaffolding without a flushPage path. Production callers must never set this flag.
- **Pause-aware dispatch.** When a transition returns a `flushPage`, the engine's `applyTransition` becomes async (awaits `flushPage.encode()`). The packet pump (`tryDispatch`) is therefore an async loop that awaits each `dispatchPacket` call before parsing the next packet — and breaks out of the loop when `paused === true` is observed, even if more buffered packets are present. A `dispatching: boolean` reentrancy guard ensures only one pump loop runs at a time; subsequent `'data'` events that arrive while the pump is awaiting just push into `recvChunks` and let the active loop drain them on its next iteration.
- **Factory failures honour the Result contract.** `transportFactory()` is awaited inside a `try` block; rejections (TLS handshake failure, cert-fingerprint mismatch, plain-TCP connect refusal) are caught and returned as `{ ok: false; reason; finalCtx }` rather than propagating as a Promise rejection. Keeps the engine's "always returns a Result" contract honest from the very first await; the orchestration shell decides whether to throw based on the Result.
- **EXIF orientation injection.** Engine-owned. Triggered when a flush completes with `side === "back"`. Replaces the per-scanner inline `setJpegOrientation` calls in both files today.
- **Page index tracking.** Engine-owned. `pageIndex` increments on each flush; `backPageIndices: number[]` accumulates indices where `side === "back"`. Both passed to `finalizeSession` at scan-end.
- **Error contract.** Unchanged from v0.3.0. Engine returns `{ ok: true } | { ok: false; reason: Error }` from its `runScanSession()` entry point. `dispatchScanSession` continues to convert `{ ok: false }` to a promise rejection — daemon and one-shot CLI see no contract change.
- **Finalize handoff.** Engine calls `finalizeSession(...)` from `src/output-tail.ts` after the graph reaches `DONE`. Existing function; no changes.

### 3.7. Engine signature

```ts
// src/scan-session.ts

export interface RunScanSessionOpts<Ctx> {
  graph: Graph<Ctx>;
  initialCtx: Ctx;
  transportFactory: SessionTransportFactory;
  outputDir: string;
  tempDir: string;
  sessionTs: Date;
  action: "jpg" | "pdf";
  paperless?: PaperlessUploadOptions;
}

export type RunScanSessionResult<Ctx> =
  | { ok: true; finalCtx: Ctx }
  | { ok: false; reason: Error; finalCtx?: Ctx };

export async function runScanSession<Ctx>(
  opts: RunScanSessionOpts<Ctx>,
): Promise<RunScanSessionResult<Ctx>>;
```

**Genericity.** `Ctx` is type-parameterised. Each scanner defines its own context shape:

```ts
// src/esci/graph.ts
export interface EsciCtx {
  duplex: boolean;
  forcedSource: Source | null;
  source: Source; // set by STATUS_2 decision
  pageCount: number;
  jpegQuality: number;
  inInterPageLoop: boolean;
}

// src/esci2/graph.ts
export interface Esci2Ctx {
  duplex: boolean;
  initPollIteration: number;
  imgChunkSize: number;
  pageEndKind: "none" | "more" | "last";
  pageSide: "front" | "back";
  zeroImgRetries: number;
  // (page index + back-page indices are engine-owned; not in Ctx)
}
```

`ctx` is the **only mutable state visible to decision functions**. No closure captures from outside the graph builder. No module-level mutables. This makes the graph reproducible and testable.

### 4.2. Scanner orchestration shells (M2 / M3)

After M1–M3, each `scanner.ts` is a thin shell — wires session config to the transport factory, threads the protocol-specific transport adapter (§3.1 finding), and translates the engine's `Result` to the existing promise-rejection contract:

```ts
// src/esci2/scanner.ts (M2 actuals: ~120 LOC after extracting the
// transport adapter to ./transport.ts; the original ~30 LOC target
// assumed no protocol teardown logic — see §3.1 M2 finding)

export async function runEsci2Scan(
  session: ScanSession,
  socketFactory: TlsSocketFactory = tls.connect,
): Promise<void> {
  // Validate temp-dir base (fail-fast before TLS handshake).
  // ... fs.accessSync(tempBase) ...
  const result = await runScanSession({
    graph: esci2Graph,
    initialCtx: { duplex: session.duplex /* ... */ },
    transportFactory: makeTlsTransportFactory(session, socketFactory), // wires withEsci2UnlockOnDestroy
    outputDir: session.outputDir,
    tempDir: session.tempDir,
    sessionTs: resolveSessionTimestamp(new Date(), session.outputDir),
    action: session.action,
    paperless: session.paperless,
  });
  if (!result.ok) throw result.reason; // dispatchScanSession contract
}
```

The graph + helpers + Ctx live in `./graph.ts`. The protocol-aware transport adapter lives in `./transport.ts`. The shell composes them.

## 5. Issue #43 fold-in

The transport-orthogonality constraint is satisfied by the design above; this section documents _how_, so a future ET-2750 PR has a one-paragraph entry point.

ET-2750 (hypothesis 1: ESC/I-2 over plain TCP) lands as:

1. A new dispatcher branch in `src/protocol-probe.ts` / `src/startup.ts:dispatchScanSession` recognising "ESC/I-2 protocol script + plain TCP transport." Detection rule TBD by the v0.3.1 protocol-diagnose mode output.
2. `src/esci2/scanner.ts` exposes a second factory variant: `makeTcpTransportFactory(session)` alongside the existing `makeTlsTransportFactory`. Cert-fingerprint logic stays in the TLS variant only. Both factories wrap their raw socket in the existing `withEsci2UnlockOnDestroy` adapter from `src/esci2/transport.ts` — same panel-hygiene rules apply over plain TCP.
3. Same `esci2Graph` runs over the new factory. **No engine changes. No graph changes. No transport-adapter changes.**

Hypothesis 2 (eSCL on port 80) would NOT use this engine — eSCL is HTTP/SOAP and shares no IS-framing or ESC/I-2 vocabulary with our engine. It would be a parallel implementation under `src/escl/` sharing only the output-tail boundary. Group A doesn't anticipate this; it would be a separate spec.

Hypothesis 3 (legacy ESC/I + different lock payload) lands as a one-line tweak in `src/esci/graph.ts`'s `WELCOME` state — the lock payload is consumer-side data, not engine-side.

## 7. Testing strategy

The regression shield is unchanged in shape: **byte-for-byte replay tests are the source of truth for protocol correctness.** New layers sit alongside, not in place of.

- **Replay tests (existing, must stay green throughout M0–M3):**
  - `src/esci2/scanner.test.ts` — 6 Frida fixtures; ESC/I-2 byte-equivalent.
  - `src/esci/scanner.test.ts` — pcap fixtures; ESC/I byte-equivalent.
- **Engine scaffolding tests (new, M1):**
  - `src/scan-session.test.ts` — pump correctness, timeout firing + suspension during barrier, flush barrier semantics (already-resolved encode promise + delayed encode promise), recv buffer drain on resume, post-flush ordering (send + next happen _after_ flush resolves, not before), decision-`{ error }` routing, page-index tracking, EXIF injection on JPG back pages, EXIF skip on PDF back pages, `"DONE"` terminal-state handling, ctx-thunk `send` resolution at dispatch time. Uses a fake transport — no real protocol bytes.
- **Graph-shape tests (new, M2 + M3):**
  - `src/esci2/graph.test.ts` — assert builder produces expected state graph (key state existence, helper-generated state targets).
  - `src/esci/graph.test.ts` — same for ESC/I, including helper-generated state names (e.g. `RESET_SRC_CMD` exists with the right `next`).

The three layers are orthogonal:

- **Graph-shape:** "Did `escEThenAck` build the right states?" Cheap, fast, unit-level.
- **Replay:** "Do the right bytes go on the wire in the right order?" Slower but authoritative.
- **Engine scaffolding:** "Does the engine handle async-flush / timeout / decision-error correctly?" Decoupled from any specific protocol.

Test-count target after M3: ≥ 320 (current 288 + ~25 engine + ~10 graph-shape; net of any consolidation).

## 8. Risks

- **Replay tests don't catch pixel-content bugs.** Exactly the gap M4 (#27 patch-sampling oracle) addresses, but M4 is out of scope here. Mitigation: M3 PR review explicitly checks the rendered output of one ADF and one flatbed pcap fixture via `npm run pcap:render`. Eyeball validation as a stop-gap. M4 brainstorm should start during M3 review so the oracle is ready before any further protocol edits.
- **M3 rewrite breaks duplex back-page rotation.** EXIF injection moves from per-scanner to engine-level. Mitigation: existing replay tests assert `Orientation=3` in EXIF on back-page JPEGs; if the engine fails to inject correctly, fixtures fail. Plus a dedicated engine unit test for `side === "back"` triggering the orientation tag.
- **Engine API gets the contract wrong, both scanners pay.** Mitigation: M1 ships and is reviewed _before_ M2/M3 begin substantive work. The engine API is shaped against scaffolding tests in isolation; if interface needs changing post-M2, it's a small refactor, not a redesign.
- **Long-lived `feature/v0.4.0-architecture` branch drifts from `dev`.** Mitigation: small frequent merges _into_ the feature branch from `dev`; each milestone PR ships back to `dev` immediately when green.
- **Sub-flow helpers cross protocol boundaries.** A reviewer might be tempted to put a shared `awaitAck` in `src/scan-session.ts`. Don't: the helpers are protocol-specific (they encode reply-byte expectations particular to that protocol). `awaitAck` for ESC/I-2 expects a 64-byte envelope; for ESC/I it expects a 1-byte ACK. Keep them in `esci2/graph.ts` and `esci/graph.ts` separately. If real cross-scanner duplication appears later, lift then.

## 9. Branch / CI strategy

- **Each milestone PR (M0–M3) is a short-lived branch off `dev` that targets `dev` directly.** Suggested branch names: `m0/protocol-naming-cleanup`, `m1/scan-session-engine`, `m2/esci2-onto-engine`, `m3/esci-onto-engine`. The v0.3.0 CI tweak already gates PRs to `dev` on `lint` / `format:check` / `test` — so each milestone PR runs the full gate by default.
- **No long-lived `feature/v0.4.0-architecture` integration branch.** An earlier draft of this spec proposed one with milestone PRs targeting it; that pattern bypasses the existing CI trigger (which only fires on PRs to `dev` or `main`), so the milestone PRs would have no enforced gate. Direct-to-`dev` is the simpler shape: smaller blast radius per merge, full CI on every PR, no extra workflow plumbing.
- **Coordination across parallel milestones (M2 and M3).** If both touch shared engine helpers (unlikely but possible), the second-to-land rebases onto `dev` after the first merges. Review-driven, not branch-driven.
- Final `dev → main` PR for the v0.4.0 release after M5–M7 land. Tag `v0.4.0`. GHCR Docker workflow auto-publishes `:v0.4.0` and `:latest`.
- **Release-note migration call-out.** v0.4.0 release notes must mention the M0 breaking-config renames (`PRINTER_PROTOCOL=legacy` → `PRINTER_PROTOCOL=esci`; `LEGACY_FORCE_SOURCE` → `ESCI_FORCE_SOURCE`) prominently, with the migration steps for any user who has these set in their env / compose file.
